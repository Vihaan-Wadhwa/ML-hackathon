## 1. Component Overview & Responsibilities

In distributed map-matching, noisy vehicle GPS observations deviate from true physical roads due to urban canyon multipath reflections, signal dropout, and low sensor sampling rates.

**Device 3** delivers the core map-matching engine:
1. **Task 1 — Road Topology & Graph Construction:** Ingesting raw geospatial network data (`.nodes` and `.arcs`), computing physical metric lengths via the spherical Haversine formula, constructing directed NetworkX `MultiDiGraph` networks that preserve parallel edges and one-way constraints, and rendering geographic road network visualizations.
2. **Task 2 (Step 1) — Device 2 ML Output Integration:** Loading candidate road predictions generated by Device 2's classifier in Parquet format supporting both `prediction_probability` and `match_probability`, performing referential integrity checks against the trip's road graph, linking GPS trajectory coordinates from `.track`, and normalizing binary match probabilities into categorical emission distributions.
3. **Task 2 (Step 2) — HMM Transition Probabilities:** Computing directed shortest-path network distances, comparing network displacement $\Delta d_{\text{net}}$ against GPS Euclidean displacement $\Delta d_{\text{gps}}$, applying exponential decay transition penalties with effective beta scaling for GPS dropouts ($> 5\text{s}$), and establishing a physical impossibility floor ($\epsilon = 10^{-6}$).
4. **Task 2 (Step 3) — Log-Space Viterbi Decoder:** Finding the global maximum-likelihood sequence of directed road arcs via dynamic programming across the observation trellis with LogSumExp row normalization, deterministic tie-breaking, and automatic nearest-road segment fallback for missing observations.
5. **Task 2 (Step 4) — GPS Coordinate Snapping & Pipeline:** Projecting GPS points perpendicularly onto Viterbi-matched road arcs with clamping $q \in [0.0, 1.0]$, strictly preserving original observation order, zero-based `obs_idx`, and elapsed timestamps in seconds.

## 5. Usage & Integration Examples

### 5.1 End-to-End Route Reconstruction (Device 4 Handoff Interface)
```python
from pathlib import Path
from modules.device3.graph.graph_builder import build_road_graph
from modules.device3.decoder.candidate_io import load_candidate_predictions, load_track
from modules.device3.decoder.reconstruction import reconstruct_trip

# 1. Construct the MultiDiGraph for the trip
road_graph, arc_lookup, stats = build_road_graph("trip.nodes", "trip.arcs")

# 2. Load GPS track and candidate predictions
track_df = load_track("trip.track")
candidates_df = load_candidate_predictions("candidates.parquet")

# 3. Reconstruct the optimal vehicle trajectory
reconstructed_df, diagnostics = reconstruct_trip(
    candidates_df=candidates_df,
    road_graph=road_graph,
    track_df=track_df,
    beta=5.0,
    return_diagnostics=True
)

# Output Schema: ['trip_id', 'obs_idx', 'timestamp', 'latitude', 'longitude', 'arc_id']
print(reconstructed_df.head())
print(f"Total Reconstruction Time: {diagnostics['total_reconstruction_time_ms']:.2f} ms")
```

### 5.2 Generating Road Network Visualizations
```python
from pathlib import Path

out_file = Path("results/my_trip_road_network.png")
visualize_road_graph(road_graph, out_file, title="Trip Road Network")
```

## 7. Device 4 Integration Specification

Device 4 can consume Device 3's output directly using:
```python
from modules.device3.decoder.reconstruction import reconstruct_trip
# or
from decoder.reconstruction import reconstruct_trip
```

### Input Requirements:
1. `candidates_df`: DataFrame containing `trip_id` (string), `obs_idx` (int64), `arc_id` (int64), and either `prediction_probability` or `match_probability` (float64).
2. `road_graph`: Directed NetworkX `MultiDiGraph` loaded via `build_road_graph(nodes_path, arcs_path)[0]`.
3. `track_df`: DataFrame containing `obs_idx` (int64), `longitude` (float64), `latitude` (float64), and `timestamp` (float64 in elapsed seconds).
4. `beta`: Transition penalty scale parameter in meters (default: `5.0`).

### Output Guarantees:
- Schema: strictly `['trip_id', 'obs_idx', 'timestamp', 'latitude', 'longitude', 'arc_id']`.
- Output length: strictly 1 snapped coordinate row per valid GPS observation.
- Referential Integrity: every `arc_id` in output is guaranteed to exist in the trip's road graph.
- Geometric Accuracy: coordinates lie on the matched road centerline within projection tolerance.
